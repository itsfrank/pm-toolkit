# Collect ingest v3 capacity plan FY27

Owner: Priya Natarajan (EM, Ingestion). Contributors: Rafael Osei, Wen Liu. Status: **Draft for FY27 planning**, last updated 2026-10-19.

## Purpose
Ingest v3 (edge receivers, spool, router) reached **100% of tenants on 2026-10-06** after the final 5% cohort was held back for a SDK retry bug. This page sizes the fleet for FY27 (Feb 2026 to Jan 2027 is FY26; FY27 is Feb 2027 to Jan 2028) and lists what must be bought, built or approved.

## Current state
- Three active ingest clusters in AWS us-east-1 (two) and us-west-2 (one, warm standby for the router).
- Edge receivers are stateless Go services behind an NLB; the spool is a replicated log on `i3en` nodes; the router forwards by tenant home region.
- Steady-state accept latency p99 is 94 ms against a 120 ms target.
- Average daily volume over September 2026 was 41 billion events.

## Capacity targets
- Per-cluster throughput target stays 400k events/s (see Kestrel Collect page).
- **FY27 aggregate headroom target: 900k events/s across three clusters**, enough for the June 2027 forecast peak with burst.
- **Edge receivers grow from 48 to 72 by 2027-04-30.**
- Spool retention window rises from 12 hours to **36 hours**, so a Warehouse writer outage of a business day does not drop events.

## Plan
1. Add 12 receivers in use1 and 12 in usw2 (spot-backed canary, on-demand for baseline).
2. Move one of the two use1 clusters' spool to `i4i` nodes for lower tail latency.
3. Promote usw2 from warm standby to active-active after load tests in February 2027.
4. Add a fourth cluster only if the June forecast is exceeded by more than 15%.

### Router change for regional tenants
Router reads `home_region` from the tenant registry and picks the writer group. Config sketch:
```yaml
router:
  default_group: wh-writers-use1
  groups:
    wh-writers-use1: { region: us-east-1 }
    wh-writers-euc1: { region: eu-central-1, enabled: false }   # Fjord, not routed yet
  spool:
    retention_hours: 36
    replication: 3
  backpressure:
    soft_limit_pct: 70
    hard_limit_pct: 90
```

### Load test queries
```sql
SELECT date_trunc('minute', received_at) AS m,
       count(*) / 60.0 AS events_per_sec,
       approx_percentile(accept_ms, 0.99) AS p99_accept
FROM ingest_audit
WHERE received_at >= now() - interval '7 days'
GROUP BY 1 ORDER BY events_per_sec DESC LIMIT 20;
```

## Appendix B: assumptions
- Event size averages 1.3 KB on the wire, 0.9 KB after compression at the edge.
- Mobile SDK batching sends every 5 s or 30 events; web SDK every 2 s.
- Receivers hold no state, so adding one takes about 4 minutes from the launch template.
- A receiver sustains about 11k events/s at 60% CPU on c7g.2xlarge; the 400k per-cluster target assumes 36 receivers.
- Spool nodes provide 7.5 TB usable each; 36 hours at forecast June peak needs 54 TB.
- Fjord adds an estimated 6% to peak volume once new EU tenants onboard; this is in the forecast but euc1 routing is disabled.

## Appendix C: FAQ
**Why not autoscale receivers?** We do, between a floor and the baseline; the plan buys the floor. *Autoscaling above the baseline is limited by NLB connection warm-up.*

**Why does spool retention matter for Warehouse outages?** Writers can fall behind; the spool is the only buffer. With 12 hours, a long Friday-evening incident could lose Saturday data.

**What about the SDK retry bug?** Web SDK 4.11 retried non-idempotent batches after a 408; fixed in 4.12 with batch ids. Duplicates are dropped in the router by batch id for 10 minutes.
