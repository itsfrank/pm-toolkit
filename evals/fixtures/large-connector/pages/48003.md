# Govern audit log pipeline runbook

Owner: Lukas Brenner (EM, Govern). Service owner: Govern team. Status: **Beta** (matches Kestrel Govern). Last reviewed 2026-10-27.

## Scope
This runbook covers the pipeline that turns product actions (role changes, login, export, policy edits) into immutable audit records visible in the Govern console and exportable to customers. It does not cover regional access policy enforcement; see the RAP initiative page.

## Architecture in one paragraph
Services emit audit events to the `govern-audit` topic. The *audit-writer* consumer validates, signs (HMAC with a per-tenant key) and writes records to the audit store (append-only tables in Warehouse). A *exporter* job pushes selected records to customer-configured destinations. Failed events go to a dead-letter queue (DLQ) with six partitions.

## Service levels
- **Delivery lag SLO: p99 under 5 minutes** from action to visible record.
- **Audit records retained 400 days** in the store, independent of the Warehouse event retention.
- Writer availability target 99.9% monthly.
- Records are immutable; corrections are new records that reference the old id.

### Lag triage
1. Open the `audit-pipeline` dashboard; note lag per partition.
2. If one partition lags, a poison message is likely; check DLQ.
3. If all lag, check Warehouse write errors (INFRA on-call).
4. Never delete topic data. Escalate to the Govern EM instead.

### Replay procedure
```bash
# dry run first; prints counts only
audit-replay --from-dlq --partition 2 --dry-run

# replay with idempotency keys (safe to repeat)
audit-replay --from-dlq --partition 2 --since 2026-10-24T00:00:00Z --batch 200

# verify
audit-verify --tenant ALL --window 2026-10-24T00:00:00Z/2026-10-25T00:00:00Z
```
Replays are idempotent by `event_id`; a second run adds zero rows.

### Verification query
```sql
SELECT date_trunc('hour', occurred_at) AS h, count(*) AS records,
       sum(CASE WHEN sig_ok THEN 0 ELSE 1 END) AS bad_sigs
FROM audit_records
WHERE tenant_id = :tenant AND occurred_at >= :from AND occurred_at < :to
GROUP BY 1 ORDER BY 1;
```

## Appendix D: how records are signed
Each record body is serialised with sorted keys, hashed with SHA-256, and signed with the tenant's current HMAC key. The record stores `key_id`, `sig` and `prev_hash`; `prev_hash` chains records per tenant per day so a missing record is detectable. The verifier recomputes the chain and reports gaps.

```json
{
  "event_id": "ev_01HXZ4",
  "tenant_id": "t_4471",
  "type": "role.changed",
  "actor": "user_882",
  "occurred_at": "2026-10-24T09:12:03Z",
  "key_id": "k-2026-09",
  "prev_hash": "9f2c...e1",
  "sig": "b71a...03"
}
```
